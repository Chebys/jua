## 1. 背景

仓库当前在三种状态之间摇摆：

1. 规范把 GC 写成 todo（原 `抽象操作.md:40`「语句块执行完毕后，对其作用域进行垃圾回收（todo）」）。
2. C++ 实现里引用计数只改了一半——[value.cpp](../../juacpp/value.cpp:173) 调用 `addRef()`/`release()`，而 [jua-value.h](../../juacpp/include/jua-value.h:33) 没有这些成员，**这直接导致当前代码无法编译**。
3. JS 实现完全依赖 V8，但自己制造了三处人为常驻对象。

只要这个决策不定，P0-1 就无法收尾，其他实现工作也都在猜。

先钉死两条事实：

**事实 A：分配量很大。** 解释器里每个中间结果都是堆对象——算术结果 `new Number`（[program.cpp:20](../../juacpp/program.cpp:20)）、每次字符串拼接 `new String`（[program.cpp:14](../../juacpp/program.cpp:14)）、每个语句块至少一个 `new Scope`（[program.cpp:247](../../juacpp/program.cpp:247) 等 6 处）、每次循环迭代两个 Scope。`for(i in 1..1000000)` 会产生约 200 万个 Scope。

**事实 B：环是常态，不是例外。** 任何一个递归函数都是环：

```
fun fact(n){ if(n<2) return 1; return n*fact(n-1) }
```

- `Declaration` 把函数写进外层作用域：`env->setProp(str, val)`（[program.cpp:49](../../juacpp/program.cpp:49)）
- `FunExpr::calc` 让函数持有那个作用域：`new Jua_PFunc(env, ...)`（[program.cpp:300](../../juacpp/program.cpp:300)，字段见 [jua-syntax.h:282](../../juacpp/include/jua-syntax.h:282)）

于是 `scope.dict["fact"] → Function.upenv → 同一个 scope`。**引用计数永远无法归零。**

此外 `Object.setProto(obj, obj)` 没有被拒绝（[vm.cpp:463](../../juacpp/vm.cpp:463)），原型链也可成环；`Scope` 同时用 `parent` 和 `proto` 两个字段指向父作用域（[jua-value.h:192](../../juacpp/include/jua-value.h:192)），引用语义还要去重。

## 2. 候选方案

| 方案 | 环 | 存量开销 | 迁移成本 | 对嵌入友好 | 结论 |
|---|---|---|---|---|---|
| A. 引用计数 | **泄漏** | 每值 +8B | 需贯穿所有 `proto=`/`dict=` 写入点 | 好（可即时释放） | **否决** |
| B. 永不回收（进程级） | 无所谓 | 0 | 0 | 差（长期宿主无法用） | **采用为 v0** |
| C. 非移动标记-清除 | 可回收 | 每值 +1 bit | 中（需根集与安全点） | 好（地址稳定） | **采用为 v1** |
| D. 移动/分代/压缩 | 可回收 | 需 forwarding 表 | 高（裸指针全部 handle 化或 pin） | 差（地址不稳定） | 否决 |
| E. 每作用域 Arena | 部分 | 低 | 高（需要逃逸分析或晋级） | 中 | 否决 |

### 为什么否决 A（引用计数）

不只是「环会泄漏」这种理论问题：**Jua 里声明一个递归函数就是在造环**，而且闭包（`local` 逃逸、方法包装）也在造环。选择 A 等于选择「大多数真实程序都会泄漏」，那还不如 B 坦诚。

若走 A 的补丁路线（弱引用、环收集器），最终会退化成一个更差的 C。

### 为什么否决 D（移动式）

值的指针以裸 `Value*` 形式存在于：C++ 局部变量、`jualist`、宿主 lambda 捕获（如 [program.cpp:134](../../juacpp/program.cpp:134) 的 `[obj, meth]`）、以及将来 C++ 宿主长期持有的句柄。移动式要么全量 handle 化（等于重写解释器），要么 pin（等于失去分代优势）。**收益（碎片整理）远小于成本。**

### 为什么否决 E（每作用域 Arena）

Jua 的语句块作用域会通过 `local` 逃逸，值也会通过 `return`、闭包、`_G[...]` 逃逸。要让 Arena 正确，必须在运行时做晋级判定——那已经是一个 GC 了，只是更绕。

## 3. 决策

### 3.1 规范层面

新增 [`draft/垃圾回收.md`](../../draft/垃圾回收.md)，核心是把 GC **从语义里摘出去**：

- 定义可达性图（属性值、原型、父作用域、函数定义作用域、原生函数捕获值、数组元素）。
- 规定「存活必须有效」「不可达不得被观察」——即 **GC 对语言语义不可见**。
- 由此推出：**实现可以永不回收**（合规）。
- 不提供终结器；`Object.id` 不得复用；内存耗尽须抛可诊断的 Jua 错误。

这样两套实现可以有不同的 GC，而语言行为仍然一致。这是 C / Lua / JS 的共同选择。

### 3.2 官方 C++ 实现：两阶段

**v0（本迭代，解 P0-1）——不回收**

- 删除 `value.cpp` 中全部 `addRef`/`release`/`ref`，`gc()` 保持 no-op。
- 文档明确「本阶段为进程级生命周期，值存活至进程结束」。
- 只要求能跑通测试与演示；长循环会吃内存，这是已知且可接受的限制。

**v1（M1 之后）——非移动、精确、stop-the-world 标记-清除**

技术方案见第 4 节。

### 3.3 JS 实现

不需要实现 GC，但必须消除人为常驻（见第 5 节）。

## 4. C++ v1 实施方案

### 4.1 值侧改动

```cpp
struct Tracer { void visit(Value*); };

struct Value {
    bool marked = false;
    virtual void trace(Tracer&) {}   // 只遍历强引用
    // ...
};
```

各类型的 `trace`：

| 类型 | 遍历 |
|---|---|
| `Object` / `Scope` | `proto`、`dict` 的值；`Scope` 额外 `parent`（与 `proto` 同值，需去重） |
| `Array` | `proto`、`items` |
| `Number` / `String` / `Boolean` / `Null` | 无（叶节点） |
| `Jua_PFunc` | `upenv` |
| `NativeFunction` | **捕获值表**（见下） |
| `Buffer` | 无（外部内存由宿主负责） |

**关键缺口：`NativeFunction` 的捕获值目前对 GC 不可见。** [program.cpp:134](../../juacpp/program.cpp:134) 的 `MethWrapper` 用 lambda 捕获 `obj` 与 `meth`：

```
let f = obj:meth      // f 逃逸，obj 只被 lambda 捕获
```

若 GC 看不到这对指针，`obj` 会被回收，`f()` 就访问野指针。因此 `NativeFunction` 需要一个显式捕获表，`MethWrapper` 构造时登记：

```cpp
struct NativeFunction: Function {
    std::vector<Value*> captures;
    void trace(Tracer& t) override { for(auto v: captures) t.visit(v); }
};
```

同理，[vm.cpp](../../juacpp/vm.cpp) 里多处 `makeFunc` 捕获 `this`（VM 指针，不是 Jua 值）——这些无需登记，但**新增任何捕获 Jua 值的原生函数都必须登记**，这是一条必须写进贡献指南的纪律。

### 4.2 根集合

| 根 | 来源 |
|---|---|
| 全局作用域 | `VM::_G` |
| 模块返回值 | `VM::modules` |
| 内置原型 | `classProto` / `NumberProto` / … 共 11 个字段 |
| 宿主句柄 | `VM::ownedValues`（已存在但**从未被写入**，v1 里启用） |
| 调用帧 | 见 4.3 |
| 待返回值 | `Controller::retval`（循环中途 `return` 的值） |
| 迭代器持有值 | 见 4.4 |

### 4.3 求值帧：为什么必须根住被调用者

```
(fun(){ ... })()      // 闭包没有名字，唯一引用在 C++ 局部变量 fn 里
```

`Call::calc` 里 `fn` 是裸指针，若它在函数体执行期间触发 GC，闭包会被回收而帧还在跑。**必须显式根住**：

```cpp
struct CallFrame { Value* callee; jualist* args; };
// VM 持有 std::vector<CallFrame> frames;
// Call::calc: 压栈 → 调用 → 出栈
```

### 4.4 安全点：只在语句边界收集

这是本方案能成立的关键简化。

`Block::exec` 是语句序列的执行点。**在两条语句之间**，C++ 栈上活跃的 Jua 值只有两个：

- `env`（当前作用域，是根）
- `controller->retval`（是根）

其余中间值都已随上一条语句的求值结束而消失。因此**不需要扫描 C++ 栈**，也不需要保守式 GC。

安全点定为：

- `Block::exec` 的每条语句之间
- `WhileStmt::exec` / `ForStmt::exec` 的回边

**唯一例外：迭代器。** `CustomIterator` 是 C++ 对象，持有 `obj` 与 `key` 两个 `Value*`（[value.cpp:17-26](../../juacpp/value.cpp:17)）。`ForStmt` 在循环体执行期间持有它，而循环体里的 `Block::exec` 会触发 GC。因此必须：

```cpp
// ForStmt::exec
it->trace(tracer);   // 把迭代器登记进根帧，或
```

或更简单：**`ForStmt` 执行期间提升 GC 抑制计数**，退出循环后允许回收。推荐后者——迭代器生命周期短，收益不值得增加 `JuaIterator::trace` 接口。

### 4.5 回收算法

- 分配时把值登记进 `VM::allValues`（`policy::unordered_set`），累计字节数超过阈值（初始 8 MiB）时置 `gcPending`。
- 安全点检查 `gcPending` → 标记（显式栈遍历，避免深递归爆栈）→ 清扫（遍历 `allValues`，未标记 `delete` 并移除）。
- 阈值按「存活量 × 2」动态调整，避免每次回收都触发下一次。
- 回收期间抑制重入（`isCollecting` 标志）。

### 4.6 与现有代码的冲突点

- **必须先完成 v0**：引用计数残留不删，v1 无从谈起。
- `Object::assignProps` 直接浅拷贝 `dict`（[value.cpp:217](../../juacpp/value.cpp:217)），在 v1 里需登记目标值——但 v1 不用引用计数，因此这条在 v0 移除 ref 调用后自然消失。
- `class()` 直接改 `proto->proto`（[vm.cpp:123](../../juacpp/vm.cpp:123)），与 GC 无冲突（proto 是强引用），但需要与 `Object.setProto` 共用入口以免将来漏遍历。
- `Buffer` 的外部内存所有权标志语义是反的（`shared=true` 表示不拥有，见 P1-8），v1 前应修正，否则 GC 释放时可能 `delete[]` 掉宿主的缓冲区。

## 5. JS 侧：不在约束范围内

`juajs` 的定位是**演示，不是生产实现**，因此本节不构成要求，只记录事实，供"将来真要把它当第二参照"时参考。

V8 负责回收，语义上不会违反 `draft/垃圾回收.md`；唯一差别是内存占用，而演示规模下不构成问题：

| 位置 | 事实 | 演示场景下 |
|---|---|---|
| [index.js:6](../../juajs/index.js:6) `convertCache` | 无上限、永不淘汰的强引用 `Map` | 进程短命，无所谓。若要修：只对 `object`/`function` 用 `WeakMap`，原始值不缓存 |
| [builtin.js](../../juajs/builtin.js) | 模块加载时永久改写 `Jua_Obj.proto` 等全局原型 | 单实例单次运行，无所谓 |
| [process.js:10](../../juajs/process.js:10) `modules` | 模块返回值永久持有 | 语义正确，规范要求的根 |

**结论**：`juajs` 侧无需任何 GC 相关工作。

## 6. 后果

**正面**

- P0-1 有明确终点：删引用计数 → 编译通过。
- 规范不再依赖实现细节，两套实现可以有不同的 GC。
- v1 方案不需要 handle 化、不需要扫栈、不需要移动值——与现有「裸指针 everywhere」的代码风格兼容。

**负面 / 风险**

- v0 阶段长循环会 OOM，属于**已知且已声明**的限制。
- v1 的 `NativeFunction` 捕获表是一条长期纪律：漏登记就是野指针。缓解手段：`makeFunc` 只保留一个构造入口，捕获 Jua 值时强制走 `makeFuncWithCaptures`。
- 无终结器意味着 `Buffer` 的外部内存必须由宿主显式管理，不能依赖回收。已在规范中写明。

## 7. 未决问题

1. **是否暴露 `gc()` 内置函数？** 建议不暴露（会引入「何时回收」的可观察性），调试用环境变量替代。
2. **弱引用 / `WeakMap` 等价物？** 推迟，等有真实用例（缓存、观察者）再谈。
3. **增量或分代？** 当前无停顿时长需求，STW 足够；若将来做多任务模式（[抽象操作.md:12](../../draft/抽象操作.md:12) 的 await），再评估增量。
4. **`Object.id` 与回收的交互**：计数器方案已满足「不复用」，无需改动。

## 8. 实现结果（2026-11-06）

v0 与 v1 已在 `juacpp/` 落地，构建入口是 [`juacpp/build.ps1`](../../juacpp/build.ps1)（`-Repl` 构建 REPL 宿主），测试入口是 [`juacpp/run-tests.ps1`](../../juacpp/run-tests.ps1)。

> **⚠ 实践教训（务必读完）**：最初只在 `Call::calc` 与 `ForStmt` 加了根，回归全绿，看着没问题。
> 后来一次运行出现 `0xC0000005`，重跑 5 次又全绿——**非确定性段错误**。
> 根因是：**任何在 C++ 局部变量上跨过一次 `calc()` 的 jua 值都必须登记为根**。
> 本次补了 7 处：二元表达式的左操作数、复合赋值的左值、`[]` 抽取的被抽取者、
> 对象/数组字面量的累积容器、`switch` 的判别值、解构的源对象与取出的值。
> 结论：安全点方案本身是对的，但「根集合」的维护是**长期纪律**，
> 每新增一个持有 `Value*` 的求值步骤，都要问一句「中间会不会触发回收」。

| 文件 | 改动 |
|---|---|
| `juacpp/gc.cpp` | **新增**。`registerValue` / `markFrom` / `safePoint` / `collect` |
| `juacpp/include/jua-value.h` | `marked` 标记位、`trace(VM*)`、`NativeFunction::captures`、`virtual ~Value()`（原先没有虚析构，删除值就是 UB） |
| `juacpp/include/jua-vm.h` | `allValues` / `gcRoots` / `markStack` / 阈值 / `RootGuard` |
| `juacpp/program.cpp` | `Block::exec` 安全点；`Call::calc` 根住被调用者与实参；`MethWrapper` 登记捕获值；`ForStmt` 根住迭代目标与键 |
| `juacpp/value.cpp` | 各类型 `trace`；删除全部引用计数残留 |
| `juacpp/test/gc.jua` | **新增** GC 回归用例 |

实测（`test.exe gc`：10 万次短命对象循环 + 5 万次成环闭包）：

```
短命对象: before=110 mid=1222 有界=true
存活值数 1569
累计回收 1298553 个值，回收 13 次
全部有界	true
```

约 130 万个值被回收，存活数稳定在 1.5k 量级；**5 万个「作用域 ↔ 闭包」环全部被回收**——正是引用计数做不到的那部分。

压力测试（30 万轮，每轮制造「对象 + 数组 + 闭包」的环，并校验闭包读到的值正确）：

```
live=4146 freed=3595969 collections=36      耗时 5809 ms   exit=0
```

30 万轮共释放 360 万个值，存活数恒定在 4k 量级，闭包读值全程正确——没有漏回收，也没有因误回收产生的悬垂指针。

实现 GC 过程中顺带暴露并修掉的阻塞/缺陷（都不在原清单里，但不修就无法验证）：

- 全仓库缺少 `using namespace Jua;`，parser/program/debug/m-json/m-math 原本各自都无法编译
- `Object::isPropTrue` 误用了继承访问，**导致类的方法完全取不到**；改为严格访问后 `class.jua` 才通过
- 函数没有原型（`FunctionProto` 创建时机过晚）
- `Buffer` 用 `delete` 释放数组、缺少 `length` 属性
- `Buffer::read` 把边界当成了下标而取模回绕
- `&&=` / `||=` 未实现短路；`is` 运算符未实现
- 迭代器的 `key` 被当成必需属性（规范写的是 `key?`）

回归：15 个用例 14 个通过。唯一失败的 `odd.jua` 是刻意的贪心解析压力测试（`0xabcdefg`、`def 'test'(v){...}`），属解析器边界，与 GC 无关。
